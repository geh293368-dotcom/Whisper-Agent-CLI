# AI 字幕优化上线流程与工程评估

记录日期：2026-06-17

## 结论

当前 AI 字幕优化流程作为“开发者诊断/效果评估”是合理的：保留原字幕，生成 `.optimized.srt`，再输出 JSON/Markdown 报告，便于比较质量、Token、费用和风险。

如果进入普通用户模式，不建议把“是否开发者模式”写成到处散落的宏或分支。建议把“优化结果如何落盘”抽象成一个明确策略：

```csharp
enum AiSubtitleOutputPolicy
{
    PreserveOriginal,      // 保留原 SRT，输出 .optimized.srt
    OverwriteWithBackup,   // 先备份原 SRT，再用优化结果覆盖原路径
}
```

推荐默认：

- 开发者诊断模式：`PreserveOriginal`，输出 `.optimized.srt` 和详细报告。
- 普通模式：`OverwriteWithBackup`，直接覆盖原字幕，但必须生成 `.bak` 或 `.original.srt` 备份。
- 不推荐 `OverwriteNoBackup`，因为 AI 可能改错，网络中断或写文件失败也需要恢复路径。

## 现有实现观察

当前核心代码在：

- `Examples/WhisperDesktop.Wpf/Services/AiSubtitleOptimizationService.cs`
- `Examples/WhisperDesktop.Wpf/Services/GeminiModelClient.cs`
- `Examples/WhisperDesktop.Wpf/MainWindow.xaml.cs`
- `Examples/WhisperDesktop.Wpf/Services/AppLogger.cs`

现有流程：

1. 根据选中视频查找同名 `.srt`。
2. 解析 SRT。
3. 每 100 条字幕调用一次 Gemini 优化。
4. 写出 `{原文件名}.optimized.srt`。
5. 再调用一次 Gemini 对比评分。
6. 写出单文件 `.ai-report.json` / `.ai-report.md`。
7. 批次完成后写出批量报告，并把摘要追加到运行日志。

这个流程的问题不是方向错，而是还缺少“生产落盘策略”和“可量化耗时指标”。当前 `developerDiagnostics` 同时影响按钮文案和评分展示，但不应该直接承担“是否覆盖原字幕”的职责。

## 耗时统计设计

用户关心的是“多少字需要多长时间”。工程上建议同时记录以下指标，后续才能建立可靠估算：

| 指标 | 说明 |
| --- | --- |
| `textCharCount` | 字幕正文字符数，不含编号和时间码 |
| `cueCount` | 字幕条数 |
| `chunkSize` | 当前为 100 条 |
| `optimizeRequestCount` | `ceil(cueCount / chunkSize)` |
| `evaluationRequestCount` | 当前为 1 |
| `totalRequestCount` | 优化请求 + 评分请求 |
| `optimizeElapsedMs` | 所有优化分块耗时 |
| `evaluationElapsedMs` | 评分耗时 |
| `totalElapsedMs` | 单文件总耗时 |
| `charsPerSecond` | `textCharCount / totalElapsedSeconds` |
| `cuesPerSecond` | `cueCount / totalElapsedSeconds` |
| `promptTokens/outputTokens/totalTokens` | 现有已有 Usage，可继续保留 |
| `retryCount` | 网络重试次数 |
| `failedChunkIndex` | 失败时定位是哪一段 |

实现上在 `OptimizeAndEvaluateFileAsync` 内部加 `Stopwatch` 即可，代码量小。更关键的是把这些字段加入 `AiSubtitleFileReport`，并在日志中输出一行单文件摘要。

建议日志格式：

```text
AI 字幕 03 地面效果3：完成，正文 5051 字，686 条，8 次请求，耗时 00:01:24，速度 60 字/秒，Token 123456，费用 ¥0.1234，输出模式 PreserveOriginal
```

失败时：

```text
AI 字幕 03 地面效果3：失败，第 4/7 段，正文 5051 字，已重试 3 次，错误 Timeout，请检查网络或稍后重试，原字幕未改动
```

## 当前样例规模

从仓库现有 SRT 抽样，正文字符数和字幕条数大致如下：

| 文件 | 正文字数 | 字幕条数 |
| --- | ---: | ---: |
| `docs/07 受击效果1.srt` | 2,117 | 258 |
| `SampleClips/ProblemCases/03 地面效果3.srt` | 5,051 | 686 |
| `SampleClips/ProblemCases/05 空中效果1.srt` | 5,920 | 740 |
| `SampleClips/ProblemCases/07 爆点制作.srt` | 8,303 | 901 |

这些数据说明：对课程类字幕来说，“视频时长”与“字数/条数”并非线性完全一致。语速、静音、重复字幕、切分粒度都会影响 AI 请求数。估时应该优先用 `cueCount` 和 `textCharCount`，视频时长只作为辅助。

## 初步耗时估算

在没有真实线上日志前，只能给工程估算。当前 HTTP 超时为 45 秒，每个文件请求数为：

```text
ceil(字幕条数 / 100) + 1 次评分请求
```

建议第一版 UI 不给过度精确的秒级估计，只显示区间和“正在根据历史运行校准”。

| 字幕规模 | 典型正文字数 | 典型字幕条数 | 当前请求数 | 可接受目标 | 风险上限 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10 分钟 | 2,000-5,000 | 200-600 | 3-7 | 30 秒-2 分钟 | 3-6 分钟 |
| 20 分钟 | 5,000-10,000 | 600-1,200 | 7-13 | 1-4 分钟 | 8-15 分钟 |
| 60 分钟 | 15,000-30,000 | 1,800-3,600 | 19-37 | 3-10 分钟 | 20-45 分钟 |
| 120 分钟 | 30,000-60,000 | 3,600-7,200 | 37-73 | 8-25 分钟 | 45-90 分钟 |

上线前需要用 10、20、60 分钟三组真实字幕跑一次，落日志后再更新估算。第一版验收目标可以定为：普通网络下，AI 优化耗时不超过原视频时长的 20% 到 30%；超过则提示用户“可后台继续”或“建议分批处理”。

## 普通模式覆盖策略

普通模式的用户期望是“生成完字幕，AI 优化后我直接拿到最终字幕”。所以可以覆盖原 SRT，但必须保证失败不破坏原文件。

推荐写入顺序：

1. 解析原 SRT，计算 hash。
2. AI 优化所有分块。
3. 渲染到临时文件：`xxx.srt.ai-tmp`。
4. 重新解析临时文件，校验条数、编号、时间码、非空正文。
5. 写备份：`xxx.original-20260617-153012.srt` 或 `xxx.srt.bak`。
6. 用临时文件替换 `xxx.srt`。
7. 写报告和日志。

任何一步失败：

- 原 `.srt` 不变。
- 临时文件可以删除或保留为诊断文件。
- 日志写明失败阶段。
- 当前文件失败不应默认中断整个批次，除非是用户取消或 API Key 无效。

## 开发者模式与普通模式边界

建议区分三类开关：

| 开关/策略 | 作用 | 默认 |
| --- | --- | --- |
| `developerDiagnostics` | 是否显示评分、详细对比和诊断报告 | false |
| `aiSubtitleOutputPolicy` | 优化结果保留副本还是覆盖原文件 | 普通模式 `OverwriteWithBackup`，开发者模式 `PreserveOriginal` |
| `autoAiOptimizeAfterTranscription` | 转录完成后是否自动 AI 优化 | false |

这样做比宏更稳。宏适合编译期移除实验功能，但这里是用户行为差异、诊断深度差异和落盘策略差异，运行时配置更适合。

如果以后要做发行版差异，可以只用编译常量设置默认值，例如 Release 默认隐藏开发者诊断入口，但核心逻辑仍然走同一套策略。

## 网络与异常处理

当前 `GeminiModelClient` 会在非 2xx 响应时抛出 `InvalidOperationException`，也有 45 秒全局超时。生产模式需要更细的错误分类。

建议分类：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 用户配置错误 | API Key 空、模型名无效、401/403 | 不重试，提示去设置页处理 |
| 限流 | 429 | 指数退避重试，失败后继续下个文件 |
| 临时服务错误 | 500/502/503/504 | 重试 2-3 次 |
| 网络波动 | DNS、连接失败、超时、请求取消但非用户取消 | 重试 2-3 次 |
| 内容错误 | 返回 JSON 为空、Schema 不匹配、字幕条数不匹配 | 可重试 1 次，仍失败则保留原字幕 |
| 用户取消 | `OperationCanceledException` 且来自用户取消 | 立即停止，写取消日志 |

重试建议：

```text
第 1 次失败后等待 2 秒
第 2 次失败后等待 5 秒
第 3 次失败后等待 10 秒
加入少量随机抖动，避免批量任务同时重试
```

每个分块应独立记录 attempt、耗时、错误码。这样网络断一下不会让用户完全不知道卡在哪。

## 是否需要上下文缓存

结论：第一版不必为“每个字幕文件全文”做显式上下文缓存，但可以调整提示词顺序，让 provider 的隐式缓存更容易命中；第二版再考虑缓存“固定资料”。

原因：

- 每个字幕文件正文不同，缓存整段字幕的复用率低。
- 当前每 100 条字幕分块，公共前缀主要是系统指令、术语提示和少量规则，体量不大。
- 10 分钟到 2 小时字幕更适合分块处理，不适合把全部内容塞进一个超长上下文。
- 真正值得缓存的是项目术语库、课程目录、固定风格规则、同一批次的领域画像，而不是每个字幕块本身。

根据 Gemini 官方文档，Gemini API 支持隐式缓存和显式缓存；隐式缓存适合短时间内相似前缀请求，显式缓存适合重复传入大段相同内容并希望保证成本收益的场景。官方也提供 `countTokens` 用于统计 token。参考：

- https://ai.google.dev/gemini-api/docs/caching
- https://ai.google.dev/gemini-api/docs/tokens

对当前工程的建议：

1. 先把系统提示、固定规则、术语提示放在 prompt 前部，字幕 JSON 放后部，提高隐式缓存概率。
2. 在报告里记录 `cachedContentTokenCount` 或等价 usage 字段；如果没有该字段就记 0。
3. 不为单个字幕文件创建显式 cache。
4. 当术语库/项目资料超过 4K token 且同一批次要处理多个文件时，再评估显式 cache。
5. 本地 LLM 后端的 KV cache 与在线 API 上下文缓存是两回事；本地后端主要关注显存占用和长上下文速度，不建议第一版复杂化。

## 代码量评估

| 工作项 | 复杂度 | 估算 |
| --- | --- | --- |
| 单文件耗时/字符数/请求数统计 | 低 | 0.5 天 |
| 报告模型新增统计字段 | 低 | 0.5 天 |
| 日志改为每完成一个文件输出摘要 | 低 | 0.5 天 |
| 输出策略枚举与配置持久化 | 中 | 0.5-1 天 |
| 普通模式覆盖 + 备份 + 临时文件校验 | 中 | 1 天 |
| 网络错误分类与分块重试 | 中 | 1-2 天 |
| 批次失败隔离，失败文件继续下一个 | 中 | 0.5-1 天 |
| UI 展示 AI 耗时/预计剩余 | 中 | 1 天 |
| 显式上下文缓存 POC | 中高 | 1-2 天，不建议第一版做 |

第一版建议控制在 4 到 6 个开发日，先做到“可测量、可恢复、可定位”。显式缓存和复杂 RAG 放到后续迭代。

## 推荐实施顺序

1. 加统计字段：字符数、字幕条数、请求数、单文件耗时、速度、重试次数。
2. 加输出策略：`PreserveOriginal` / `OverwriteWithBackup`。
3. 把普通模式覆盖做成安全事务：临时文件、校验、备份、替换。
4. 增加网络重试和错误分类。
5. 日志改为单文件完成即输出摘要，批次完成再输出汇总。
6. 用真实 10/20/60 分钟字幕跑基准，更新估时表。
7. 再评估是否引入显式缓存或 RAG。

## 验收标准

- AI 优化成功后，普通模式下原 `.srt` 被优化结果覆盖，旁边存在可恢复备份。
- 开发者模式下原 `.srt` 不变，生成 `.optimized.srt` 和完整报告。
- 任意网络失败、JSON 解析失败或校验失败时，原字幕不被破坏。
- 日志能定位到文件、分块、耗时、重试次数、Token、费用和输出路径。
- 报告能回答“这个文件多少字、多少条、用了多久、平均每秒多少字”。
- 批量任务中单个文件失败不会吞掉其他文件的优化机会。
- 上下文缓存第一版不作为上线阻塞项。
