# 实时字幕功能设计

状态：第一版已实现  
记录日期：2026-06-15  
更新日期：2026-06-15  

## 1. 目标

实时字幕用于从麦克风持续采集声音，在用户说话后尽快生成可阅读、可保存的字幕。

第一版的目标不是直播平台级的逐字滚动，而是稳定的“低延迟逐句字幕”：

- 检测到说话后开始收集音频。
- 检测到一句话结束或达到最长片段时执行识别。
- 通常在停顿后约 0.5 至 1.5 秒显示确认字幕。
- 长时间静音不产生空字幕或 Whisper 幻觉。
- 会话结束后可以复制或导出 TXT、SRT。

这种方式更适合课程讲解、会议记录、口述和教学演示，也更符合当前本地模型的能力边界。

## 2. 当前实现情况

第一版实时字幕已经完成。当前实现采用旧 D3D11 兼容流式链路：

- React 已提供“实时字幕”页面、麦克风选择、语言选择、状态展示、字幕列表、复制和导出入口。
- WPF 宿主负责录音设备枚举、模型状态、消息桥接、会话状态和导出文件。
- `LiveTranscriptionService` 使用 `iAudioCapture` 与 `Context.runCapture()` 完成麦克风采集、VAD 分句和持续识别。
- 默认参数为 2 秒最短片段、8 秒最长片段、300ms 开头静音裁剪和 600ms 停顿判断。
- 页面显示聆听、检测到说话、识别中和处理延迟等状态。
- 会话结束后可清空、复制全部、导出 TXT 或导出 SRT。

当前第一版没有接入 whisper.cpp CUDA 实时会话。CUDA/CPU 后端仍用于批量文件转录；实时字幕使用 `Whisper.dll` 兼容流式能力。后续如需统一到 CUDA，需要新增托管 PCM 采集、VAD 队列和片段推理接口，或扩展 whisper.cpp 后端的实时 ABI。

### 2.1 实现前基础

当前 React 页面已经具备：

- “实时字幕”导航和页面入口。
- 麦克风设备列表。
- 刷新设备按钮。
- 语言选择。
- 字幕显示区域占位。

WPF 宿主已经具备：

- Media Foundation 初始化。
- 录音设备枚举。
- 设备选择状态。
- 模型加载状态和桌面消息桥接。

旧版桌面程序和 `MicrophoneCS` 示例还提供了完整参考：

- `iAudioCapture` 打开麦克风。
- `Context.runCapture()` 持续识别。
- VAD 风格的语音开始和停顿切片。
- `Listening`、`Voice`、`Transcribing`、`Stalled` 状态。
- 默认 7 秒最短片段、11 秒最长片段、250ms 开头静音裁剪和 333ms 停顿判断。

旧流程使用 D3D11 的 `Context.runCapture()`。当前主推的 whisper.cpp CUDA 后端只暴露整块 PCM 的 `wd_transcribe()`，尚未提供实时会话或原始麦克风 PCM 接口。因此第一版先复用 D3D11 流式链路完成产品闭环，CUDA 实时链路保留为后续架构工作。

## 3. 产品范围

### 3.1 第一版必须支持

- 选择麦克风。
- 显示输入音量。
- 开始和停止实时字幕。
- VAD 检测说话和静音。
- 逐句生成确认字幕。
- 显示运行时间、当前状态和处理延迟。
- 清空、复制和导出本次字幕。
- 模型未加载、设备不可用、权限失败和处理跟不上时给出明确提示。
- 停止后正确释放麦克风和后台任务。

### 3.2 第一版暂不支持

- 直播软件透明悬浮字幕窗。
- 系统声音或扬声器回环采集。
- 多说话人识别和说话人姓名。
- 逐字级稳定字幕。
- 实时翻译与原文双语同时显示。
- 自动降噪、声源分离和背景音乐分类。
- 多麦克风混音。

这些功能可以后续增加，但不应扩大第一版的技术风险。

## 4. UI 页面设计

建议把当前两列设置页改为“顶部控制区 + 中部字幕区 + 底部操作栏”。

### 4.1 页面头部

显示：

- 标题：`实时字幕`。
- 简介：`从麦克风采集语音，逐句生成字幕`。
- 模型状态：`模型已就绪`、`模型加载中` 或 `请先加载模型`。
- 会话状态圆点：灰色空闲、绿色聆听、蓝色识别、橙色延迟、红色错误。

### 4.2 录音设备区

必要元素：

| 元素 | 作用 |
| --- | --- |
| 麦克风下拉框 | 选择录音设备 |
| 刷新设备 | 重新枚举插拔后的设备 |
| 输入音量条 | 确认麦克风是否收到声音 |
| 设备状态文字 | 显示可用、断开、占用或权限失败 |

建议增加“测试麦克风”按钮，但它不是第一版必需。实时会话开始后，设备下拉框和刷新按钮应禁用。

### 4.3 识别设置区

第一版只展示高价值选项：

- 源语言。
- 延迟与稳定性预设。
- 语音检测灵敏度。
- 自动保存开关。

延迟预设建议使用用户可理解的名称：

| 预设 | 建议行为 | 适用场景 |
| --- | --- | --- |
| 快速 | 约 2–5 秒音频片段，较短停顿即提交 | 对话、演示 |
| 均衡（默认） | 按语句停顿提交，最长约 8 秒 | 课程、会议 |
| 稳定 | 允许更长上下文，最长约 12 秒 | 连续讲解、准确性优先 |

高级参数如停顿毫秒数、前后缓冲和最大队列长度不应直接放在第一层界面。

### 4.4 会话控制区

主按钮：

- `开始实时字幕`：空闲时显示。
- `停止`：运行时显示，点击后完成当前片段并结束会话。

辅助按钮：

- `暂停` / `继续`：可以作为第二阶段功能。暂停需要明确是停止采集还是继续采集但不识别，第一版先不加入可减少状态复杂度。
- `清空字幕`：运行中需要二次确认或只清空界面、不重置会话时间。

开始按钮启用条件：

- 模型已加载。
- 已选择可用麦克风。
- 没有批量转录、模型加载或其他实时会话占用同一引擎。

### 4.5 运行状态区

实时显示四类状态：

- `正在聆听`：麦克风已打开，当前没有检测到人声。
- `检测到说话`：正在积累当前语句。
- `正在识别`：音频片段已送入模型。
- `处理延迟`：识别速度低于音频产生速度，队列正在增长。

同时显示：

- 会话时长，例如 `00:18:42`。
- 已确认字幕条数。
- 最近一次识别耗时，例如 `0.8 秒`。
- 当前待处理音频，例如 `2.4 秒`。

不建议显示传统百分比进度，因为实时会话没有固定终点。

### 4.6 字幕显示区

字幕区域分为两层：

1. 当前语句区：显示 `正在聆听...`、音量波形或尚未确认的临时文本。
2. 已确认字幕列表：按时间顺序滚动显示最终字幕。

每条确认字幕包含：

- 开始时间。
- 结束时间。
- 字幕正文。
- 可选的复制按钮。

最新字幕应自动滚动到可见区域，但用户手动向上查看历史后，应暂停自动滚动，并显示“回到最新”按钮。

第一版可以不做临时识别文本，只显示声音活动和已确认字幕。这样可避免文本反复变化带来的视觉抖动和误解。

### 4.7 底部操作栏

建议按钮：

- `清空`。
- `复制全部`。
- `导出 TXT`。
- `导出 SRT`。
- `打开保存位置`，仅在已经保存后显示。

自动保存开启时，应在状态栏显示实际文件路径，并采用增量写入，降低应用异常退出时丢失整场字幕的风险。

## 5. 实时处理流程

推荐数据流：

```text
麦克风/WASAPI
  -> 16kHz 单声道 PCM
  -> 音量统计与 VAD
  -> 语音片段缓冲区
  -> 后台识别队列
  -> whisper.cpp CUDA
  -> 时间戳校正与文本去重
  -> React 实时字幕列表
  -> 可选 TXT/SRT 增量保存
```

### 5.1 音频格式

Whisper 输入统一为：

- 16kHz。
- 单声道。
- 32 位浮点 PCM，范围约为 `-1.0` 至 `1.0`。

设备原始采样率可能是 44.1kHz 或 48kHz，采集层应负责重采样，不能让 React 或转录层处理设备格式差异。

### 5.2 VAD 与切片

推荐初始参数：

- 语音前置缓冲：250–350ms。
- 语音后置缓冲：250–500ms。
- 判定一句结束的静音：500–700ms。
- 最短提交语音：约 1.5 秒。
- 最长片段：8–10 秒。

旧版默认最短 7 秒、最长 11 秒，稳定但实时感偏弱。新版应主要依赖自然停顿提交，而不是必须等满 7 秒。

VAD 的作用：

- 跳过长时间静音。
- 降低静音幻觉字幕。
- 减少无效 GPU 推理。
- 让语句在自然停顿处结束。

VAD 不能替代降噪，也不能可靠区分带人声的歌曲和正常讲话。

### 5.3 识别队列

音频采集线程绝不能等待模型推理，否则会导致麦克风样本丢失。

建议使用有界队列：

- 采集线程只负责写入 PCM 和 VAD 切片。
- 单独的推理工作线程顺序处理语音片段。
- 队列容量建议为 2 至 3 个片段。
- 队列积压时显示“处理延迟”。
- 不应静默丢弃音频；确实必须丢弃时应记录日志并在界面提示。

当前 CUDA 批量速度远快于实时音频，正常硬件上通常不会积压，但 CPU 后端、大模型或系统高负载时仍需保护。

### 5.4 临时字幕与确认字幕

逐字临时字幕需要反复识别正在增长的音频窗口，会增加 GPU 调用、重复文本和界面抖动。

建议分阶段实现：

- 第一版：只在 VAD 完成一句切片后生成确认字幕。
- 第二版：每 0.8 至 1.2 秒对当前语句做一次低频临时识别。
- 临时文本只显示在“当前语句”区域，不能立即写入 SRT。
- 语句结束后用最终识别结果替换临时文本并写入历史。

### 5.5 时间戳

每个 PCM 样本在会话中都有绝对位置。字幕最终时间戳应这样计算：

```text
字幕绝对时间 = 语音片段在会话中的起点 + Whisper 返回的片段相对时间
```

不能直接把每次 `whisper_full()` 返回的时间从零开始显示，否则每个音频块都会重复从 `00:00:00` 开始。

暂停、设备重连和丢帧都要明确是否计入会话时间。第一版建议 SRT 使用真实会话流逝时间，保留停顿间隔。

### 5.6 上下文连续性

当前 CUDA 批量后端设置了 `no_context = true`。实时字幕如果每句话完全独立，专业术语和代词连续性可能变差。

建议只携带最近 1 至 2 条已确认字幕作为短上下文提示，避免无限累积：

- 改善课程术语连续性。
- 减少一句话被切开后上下文丢失。
- 避免错误文本长期污染后续识别。

第一版也可以先保持无上下文，待基本链路稳定后再加入短上下文。

## 6. 后端实现选择

### 6.1 方案 A：直接使用旧 D3D11 `runCapture`

优点：

- 现有代码和示例完整。
- 内置采集、语音切片、状态回调和连续识别。
- 最快得到可运行原型。

缺点：

- 不使用当前主推的 whisper.cpp CUDA 后端。
- 用户切到 CUDA 后仍可能需要单独加载 D3D11 模型。
- 两套推理行为和性能难以统一。

适合做技术验证，不适合作为最终默认实现。

### 6.2 方案 B：托管层采集 PCM，复用 CUDA 分块转录

使用 WASAPI/Media Foundation 或成熟的托管音频库采集 PCM，然后把完成的语音片段送入现有 `wd_transcribe()`。

优点：

- 可以复用当前 CUDA 模型和大部分转录代码。
- 采集、VAD、队列和 UI 状态容易在 C# 管理。
- 便于单元测试状态机和切片逻辑。

缺点：

- 当前 `iAudioCapture` 对 C# 是不透明接口，不能直接读取 PCM。
- 需要扩展现有 Media Foundation 封装，或增加新的 WASAPI 采集依赖。
- 需要为重采样、设备断开和缓冲溢出负责。

这是推荐的长期方案。

### 6.3 方案 C：在 `WhisperCppBackend` 中实现完整原生实时会话

让 C++ DLL 同时负责 WASAPI、VAD、缓冲和 whisper.cpp 推理，再向 C# 报告状态和字幕。

优点：

- 原生数据路径短。
- 可以集中控制缓冲和 whisper.cpp 上下文。
- C# 只消费事件。

缺点：

- C++ 状态机、线程、回调和资源释放复杂。
- UI 功能变化通常需要修改原生 ABI。
- 测试和故障排查成本最高。

除非后续性能数据证明托管采集成为瓶颈，否则不建议第一版采用。

### 6.4 推荐路线

当前第一版已经采用方案 A，复用旧 D3D11 `runCapture` 完成实时字幕闭环。这是最快、风险最低的落地路径。

后续如果要让实时字幕与批量转录共用 whisper.cpp CUDA 模型，推荐再演进到方案 B，并借用旧 `runCapture` 的参数和状态设计：

1. 建立 `ILiveAudioCapture`，负责设备、PCM、音量和断开事件。
2. 建立 `LiveTranscriptionSession`，负责 VAD、切片、队列、状态机和保存。
3. 为 `ITranscriptionEngine` 增加实时片段识别能力，或建立独立的 `ILiveTranscriptionEngine`。
4. CUDA 实现复用已加载模型，对语音片段调用 whisper.cpp。
5. D3D11 保留为兼容流式实现，但 UI 与状态模型共用。

不要把实时会话逻辑继续堆进 `MainWindow.xaml.cs`。它应只负责命令转发和向 WebView 发布状态。

## 7. 建议的代码边界

```text
MainWindow
  -> LiveTranscriptionController
       -> ILiveAudioCapture
       -> IVoiceActivityDetector
       -> ILiveTranscriptionEngine
       -> LiveSubtitleWriter
```

建议数据模型：

```csharp
enum LiveSessionState
{
    Idle,
    Starting,
    Listening,
    VoiceDetected,
    Transcribing,
    Stopping,
    Failed,
}

record LiveSubtitleSegment(
    int Index,
    TimeSpan Begin,
    TimeSpan End,
    string Text,
    bool IsFinal);
```

WebView 消息建议：

- `startLive`。
- `stopLive`。
- `clearLiveSegments`。
- `exportLive`。
- `liveStateChanged`。
- `liveLevelChanged`。
- `liveSegmentAdded`。
- `livePartialChanged`。

音量事件更新频率控制在每秒 10 至 20 次，字幕和状态按事件发送，避免高频消息压垮 WebView。

## 8. 状态机

```text
Idle
  -> Starting
  -> Listening
  -> VoiceDetected
  -> Transcribing
  -> Listening
  -> Stopping
  -> Idle
```

任一活动状态发生不可恢复错误时进入 `Failed`，完成资源释放后允许回到 `Idle`。

重要规则：

- 同一时间只能有一个实时会话。
- 实时会话与批量任务不能同时使用同一个模型上下文。
- 停止操作必须可重复调用。
- 设备断开时自动停止并保留已生成字幕。
- 窗口关闭时先取消采集，再等待推理线程安全退出。

## 9. VAD、噪声和音乐

实时字幕必须考虑 VAD。没有 VAD 时，静音、风扇声和背景噪声会增加无效推理，并可能产生幻觉字幕。

第一版建议：

- 默认开启 VAD。
- 提供低、标准、高三档灵敏度，默认标准。
- 显示“未检测到人声”，而不是把静音送去识别。
- 为句首保留前置音频，避免切掉第一个字。
- 对过短、能量很低的片段直接忽略。

纯乐器背景音乐通常可以被语音检测过滤，但带歌词的音乐与讲话相似，普通 VAD 无法可靠区分。第一版不需要加入音乐分类或人声分离；只需在文档和设置说明中明确限制。

## 10. 保存策略

第一版建议支持：

- 内存中保存本次确认字幕。
- 手动导出 TXT 和 SRT。
- 可选自动保存。

自动保存应使用临时会话文件并增量追加。停止后再生成最终 SRT，避免每新增一句就重写整个大文件。异常退出后可从临时文件恢复已确认字幕。

临时文本不能写入最终文件，只有确认字幕可以持久化。

## 11. 错误处理

| 情况 | 界面行为 |
| --- | --- |
| 模型未加载 | 禁用开始按钮并引导到模型设置 |
| 没有麦克风 | 显示未发现设备并提供刷新 |
| 麦克风权限失败 | 显示 Windows 权限提示和具体错误 |
| 设备被拔出 | 停止会话，保留已生成字幕 |
| 设备被占用 | 显示打开失败，不自动循环重试 |
| 推理队列积压 | 显示处理延迟和待处理秒数 |
| 单个片段识别失败 | 记录错误，可继续后续片段 |
| 模型或原生后端崩溃风险 | 终止会话，不静默丢失字幕 |

## 14. 验收标准

- 模型和麦克风可用时能够开始实时会话。
- 连续说话 30 分钟不出现明显内存持续增长。待长时实测。
- 长时间静音不生成字幕。依赖当前 VAD 流式链路，仍建议用真实会议/课程场景复测。
- 正常语句停顿后约 0.5 至 1.5 秒出现确认字幕。
- 输入音量和状态变化可见，页面操作保持流畅。
- 识别线程繁忙时不阻塞音频采集。
- 停止后麦克风立即释放，能够再次开始。
- 拔出麦克风、取消和关闭窗口不会导致进程卡死。待硬件插拔专项复测。
- 导出的时间戳按整场会话连续增长，不会每个片段从零开始。
- 已确认字幕可以复制并导出为有效 TXT、SRT。

## 15. 最终建议

实时字幕第一版已经实现，可以作为当前发行版的可用功能保留。

当前实现定位仍是“VAD 驱动的低延迟逐句字幕”，不是复杂的逐字字幕。第一版先复用 D3D11 兼容流式引擎完成麦克风字幕闭环，后续再评估是否用托管 PCM 采集 + whisper.cpp CUDA 片段推理统一引擎模型。
