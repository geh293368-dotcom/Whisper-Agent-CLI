# 任务完成时间估算与模型自动加载设计

状态：第一版已实现  
记录日期：2026-06-15  
更新日期：2026-06-15  

## 1. 文档范围

本文统一记录两项与等待体验有关的功能：

- 批量字幕任务的预计剩余时间与预计完成时间。
- 应用启动时自动加载上次选择的模型。

两项功能共用“后台执行、持续反馈、失败可恢复”的设计原则，放在同一份文档便于统一实现和验收。

### 1.1 当前实现摘要

两项功能第一版已经完成：

- 批量字幕会在导入文件时读取媒体时长，并在任务运行时显示总时长、已处理、已用时、实时速度、预计完成时刻和剩余时间。
- ETA 使用已处理媒体秒数与墙钟耗时计算，并使用 0.8/0.2 的指数平滑降低跳动。
- ETA 至少运行 10 秒、处理 2 分钟媒体或完成一个有时长文件后才显示。
- 未知时长文件不参与估算，界面会提示有多少未知时长文件未计入。
- 启动时自动加载上次模型已实现，配置项为 `AutoLoadModel`，默认开启。
- 自动加载在 WebView/React 初始化后触发，并有一次性保护，避免重复初始化时重复加载。
- 模型加载阶段显示已用时间；CUDA/CPU 后端使用不确定型进度，D3D11 使用真实进度回调。
- 加载期间禁用模型路径、推理引擎和开始转录等易造成状态错乱的操作。

## 2. 字幕任务 ETA 评估

### 2.1 日志样本

本次分析了 `2026-06-11` 至 `2026-06-15` 的本地日志，共提取到 485 个已完成文件和 5 个完整批次。

| 指标 | 结果 |
| --- | ---: |
| 单文件速度平均值 | 71.6x |
| 单文件速度中位数 | 71.2x |
| 单文件速度 P10 | 46.5x |
| 单文件速度 P90 | 96.9x |
| 单文件最低速度 | 22.7x |
| 单文件最高速度 | 139.0x |
| 完整批次速度范围 | 43.3x - 85.9x |

按典型速度换算，1 小时媒体通常约需 1 分钟；按 P10 的保守速度约需 1 分 17 秒。由于音频内容、模型、推理后端、文件解码和长文件特征都会影响速度，历史固定速度只能作为任务刚开始时的参考，不能作为整个任务的唯一依据。

### 2.2 实现结论

ETA 已实现，而且现有代码已经使用主要数据：

- 导入时读取媒体总时长。
- 转录引擎持续报告当前文件进度。
- 批次秒表记录实际墙钟耗时。
- 已完成文件记录媒体时长和处理耗时。

当前核心公式：

```text
实时速度 = 已处理媒体秒数 / 已用墙钟秒数
剩余秒数 = 剩余媒体秒数 / 平滑后的实时速度
预计完成时间 = 当前时间 + 剩余秒数
```

其中“已处理媒体秒数”应包含已完成文件的完整时长，以及当前文件时长乘以当前进度。

### 2.3 推荐展示

批量任务底部建议显示：

```text
总时长 56:24:36 · 已处理 18:42:10 · 已用时 18:06 · 速度 62.0x
预计 10:14 完成 · 剩余约 36 分钟
```

任务刚开始、样本不足时显示：

```text
正在估算完成时间...
```

当前满足以下任一条件后再给出 ETA：

- 已运行至少 10 秒。
- 已处理至少 2 分钟媒体。
- 已完成第一个短文件。

### 2.4 稳定性策略

不能直接使用瞬时速度，否则 ETA 会频繁跳动。第一版已经加入指数平滑：

```text
平滑速度 = 旧速度 * 0.8 + 新采样速度 * 0.2
```

界面更新频率建议限制为每秒一次。转录进度本身可以更频繁更新，但 ETA 没有必要每 200 毫秒重算和重绘。

预计完成时间可按分钟取整，剩余不足 10 分钟时再显示到分钟级。不要显示到秒，因为实际误差远大于一秒。

### 2.5 未知时长文件

当前实现已经允许部分文件时长未知：

- 已知时长文件继续参与 ETA。
- 未知时长文件不计入公式。
- 界面提示未知时长文件数量。
- 如果所有文件时长都未知，则不显示 ETA。

这样能保留大部分估算价值，也不会把不完整结果伪装成完整结果。

### 2.6 初始估算

在任务尚未产生有效进度前，可以用历史速度给出低置信度初始值。建议按以下维度保存最近 5 至 10 个成功批次的加权速度：

- 推理引擎，例如 CUDA、CPU 或 D3D11。
- 模型文件标识，可使用完整路径、文件大小和最后修改时间组合。
- 语言与翻译模式。

没有匹配历史时，可暂用当前日志的保守基线 `50x`，但界面应显示“初步估算”。运行 10 秒后切换为本批次实时估算。

第一版也可以不持久化历史速度，只在本批次运行后显示 ETA。这样实现更简单，可信度也足够高。

### 2.7 验收标准

- 已知时长文件全部选中时，任务运行约 10 秒后出现 ETA。
- ETA 随任务推进更新，但不会每秒大幅来回跳动。
- 显示剩余时间和预计完成时刻。
- 存在未知时长文件时仍显示已知部分估算，并显示未计入数量。
- 停止、失败、重新开始和重新选择队列后，旧 ETA 不残留。
- 批次完成时 ETA 清空，最终日志保留总时长、总耗时和平均速度。

## 3. 模型自动加载评估

### 3.1 当前实现

启动自动加载已经完成。现有实现包括：

- 配置保存 `ModelPath`、最近模型、所选推理引擎和 `AutoLoadModel`。
- React 初始化后触发 `TryAutoLoadModelAsync()`。
- `autoLoadAttempted` 防止页面重复初始化导致重复加载。
- 文件不存在时跳过自动加载并给出状态和日志。
- 加载成功、取消和失败都会恢复界面状态，并允许用户手动处理。

### 3.2 实现前基础

现有实现已经具备自动加载所需的大部分条件：

- `config.json` 会保存 `ModelPath`、最近模型和所选推理引擎。
- `LoadConfig()` 会在窗口构造阶段恢复这些配置。
- `LoadModelAsync()` 已有加载中、成功、取消和失败状态。
- React 页面已有模型状态和进度条。
- whisper.cpp CUDA/CPU 的同步原生加载已包装在 `Task.Run` 中，不会占用 WPF UI 线程。
- D3D11 加载接口本身提供异步调用和进度回调。

因此，启动时自动加载是可行的，改动范围较小。

### 3.3 触发时机

自动加载没有放在 `MainWindow` 构造函数里。当前在前端首次发送 `initialize` 命令后执行：

```csharp
case "initialize":
    PublishState();
    await TryAutoLoadModelAsync();
    break;
```

同时增加一次性保护，避免页面刷新或重复初始化导致模型重复加载：

```csharp
bool autoLoadAttempted;

async Task TryAutoLoadModelAsync()
{
    if (autoLoadAttempted)
        return;

    autoLoadAttempted = true;
    if (!string.IsNullOrWhiteSpace(modelPath) && File.Exists(modelPath))
        await LoadModelAsync();
}
```

这一时机的优点是界面已经可以立即显示“正在加载模型”，而耗时工作仍在后台线程执行，窗口可以正常移动、切换页面和查看日志。

### 3.4 配置策略

`AppConfig` 已增加：

```csharp
public bool AutoLoadModel { get; set; } = true;
```

模型与设置页已增加“启动时自动加载上次模型”开关，默认开启。保留开关更容易处理以下情况：

- 用户暂时不想占用显存。
- 用户需要先切换 CUDA、CPU 或 D3D11 后端。
- 大模型加载时间较长。
- 排查模型或驱动问题时需要禁用自动行为。

### 3.5 进度条方案

当前不同引擎的进度精度不一致：

- D3D11 路径可以获得真实的连续加载进度。
- whisper.cpp CUDA/CPU 当前只报告约 `5%` 和 `100%`，中间原生加载没有连续回调。

因此不应让 CUDA 进度条长时间停在 5%，这容易让用户误以为程序卡住。当前采用混合展示：

- 有真实连续进度时，显示确定型百分比进度条。
- 只有开始和完成事件时，显示不确定型滚动进度条。
- 状态文字显示 `正在加载模型，已用时 4 秒`。
- 完成后切换为 100%，显示 `已加载 model-name.bin`。

用户真正需要的是确认程序仍在工作，而不是一个看似精确但并不真实的百分比。

如果以后必须提供“大致百分比”，可记录相同引擎和模型文件的历史加载耗时，用历史中位数驱动 5% 到 90% 的平滑动画；真实加载结束时再跳到 100%。该值必须标记为估算，不应混同为真实进度。

### 3.6 加载时界面行为

加载期间当前行为：

- 页面导航、日志查看和普通窗口操作保持可用。
- 禁止开始转录。
- 禁止切换推理引擎、模型路径和再次点击加载。
- 提供取消加载按钮；复用 `CancellationTokenSource`。
- 关闭窗口时沿用现有确认逻辑。

### 3.7 失败与回退

自动加载失败不应阻止应用进入主界面，也不应自动反复重试。

| 情况 | 推荐行为 |
| --- | --- |
| 路径为空 | 保持“尚未选择模型” |
| 文件不存在 | 显示“上次模型文件不存在”，保留手动选择入口 |
| 模型损坏或格式不支持 | 显示错误，记录日志，不再自动重试 |
| CUDA 后端不可用 | 显示加载失败，允许用户切换 CPU 或 D3D11 |
| 用户取消 | 显示“模型加载已取消”，允许手动重试 |
| 页面重复初始化 | 一次性保护阻止重复加载 |

不建议在 CUDA 失败后静默自动切换 CPU，因为这可能造成速度和资源占用与用户预期不一致。

### 3.8 模型切换行为

“启动时自动加载”与“设置页选择模型后立即加载”应分开设计。

第一版当前行为：

- 启动时：有效路径存在且自动加载开启时自动加载。
- 运行中更换模型路径：只更新选择，仍由用户点击“加载模型”。
- 切换推理引擎：卸载旧模型，提示需要重新加载。

这样可避免用户只是浏览下拉选项时就意外卸载当前模型或触发大文件加载。后续如果确实需要“选择即加载”，应增加防抖、确认和加载失败回滚。

### 3.9 日志与性能数据

当前日志已经记录模型加载开始、完成和耗时：

```text
[模型] 开始自动加载：模型名；引擎 CUDA；文件大小 1.5 GB
[模型] 加载完成：耗时 3.8 秒
```

失败时记录路径、引擎、耗时和异常。后续可以根据真实数据决定是否值得实现历史加载时间估算。

### 3.10 验收标准

- 配置中存在有效模型路径时，应用启动后自动开始加载。
- 自动加载只触发一次，页面刷新不会重复加载。
- 加载期间窗口和 React 界面保持响应。
- 用户可以看到加载状态、活动进度和已用时间。
- 加载完成后无需再次点击按钮即可开始转录。
- 路径失效或模型加载失败时，应用仍可正常使用并允许重新选择。
- 加载期间不能切换引擎或模型路径造成状态错乱。
- 日志记录自动/手动来源、模型、引擎、结果和耗时。

## 5. 最终建议

两项功能第一版已经实现。

- 字幕 ETA 以当前批次实时速度为主，暂未引入历史速度初始估算。
- 模型自动加载默认开启但保留关闭选项，在 React 页面初始化完成后触发。
- CUDA 模型加载阶段优先使用活动进度条和已用时，不制造虚假的精确百分比。
- 所有失败都应可恢复，不能因为自动行为让用户无法进入正常工作流程。
